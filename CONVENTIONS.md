# Conventions

Patterns introduced as the codebase grows, in the order they showed up. `CLAUDE.md` is the source of truth for *what* to build; this file records *how* we've been building it, so a new pattern doesn't get reinvented differently next time.

## Enums, not magic strings

PHP backed enums live in `app/Enums`. `App\Enums\UserRole` (`admin`/`buyer`/`vendor`) backs the `users.role` column. Status/rank/method enums for `part_requests`, `vendor_responses`, etc. should follow the same shape as they're introduced.

## Model casts: use the `$casts` property, not the `casts()` method

Laravel 11+ supports both `protected $casts = [...]` and `protected function casts(): array`. **Use the property form.** Larastan 3.10 doesn't resolve enum/type casts declared via the `casts()` method — it falls back to inferring the attribute's type straight from the DB column (e.g. an `enum` column becomes a string-literal union), which produces false-positive "always false" errors on strict enum comparisons (`$user->role === UserRole::Admin`). The property form is equally idiomatic and Larastan resolves it correctly.

## Settings

`App\Models\Setting` is a key/value/type store (`settings` table). Read with `Setting::get(string $key, mixed $default = null)` — casts the stored value based on its `type` column (`integer`, `boolean`, else raw string). Write with `Setting::set(string $key, mixed $value, string $type = 'string')`.

## PricingService

`App\Services\PricingService::calculate(int $costPrice): array` is the single source of truth for margin pricing (§6.1 of `CLAUDE.md`). Returns `cost_price`, `applied_rate`, `applied_min_fee`, `margin`, `buyer_price` — the four snapshot fields plus the input, ready to persist onto a `part_request` at quote-presentation time (§6.2: never recompute a historical order from live settings). Every caller that needs a price goes through this service — do not reimplement the `max(percentage, floor)` rule elsewhere.

## Livewire's bundled Alpine — don't add a separate `alpinejs` package

Livewire 3 ships its own internal build of Alpine.js and boots it automatically via `@livewireScripts`. Installing `alpinejs` as a separate npm dependency causes a double-initialization conflict. Alpine is available on every page that includes `@livewireScripts` — no extra import needed.

## spatie/laravel-activitylog: attribute changes live in `attribute_changes`

On the installed 5.x line, a logged model's attribute diff is on the `attribute_changes` column (`['attributes' => [...], 'old' => [...]]`), not on `properties` (which comes back empty for a plain `LogsActivity` model) and not via a `changes()` method — both exist in older docs/versions but not this one. See `VendorProfile`/`VendorProfileTest` for the working pattern.

**A test asserting on activity log rows must filter on `subject_type`, not just `subject_id`.** `subject_id` alone is just the subject's own auto-increment id, and every `LogsActivity` model shares the same `activity_log` table — two unrelated models can easily land on the same numeric id in a fresh `RefreshDatabase` test (e.g. a factory chain that creates a `BuyerProfile` as a side effect ends up with `id=1`, same as the `PresentedQuote` under test). `Activity::query()->where('subject_id', $model->id)->latest()->first()` can silently return a *different* model's activity row instead — passing assertions on the wrong data, or (as happened writing `PresentQuoteActionTest`'s override-logging case) throwing "undefined array key" because that other row's `attribute_changes` doesn't have the key you're checking. Always add `->where('subject_type', Model::class)` alongside `subject_id`.

## Vendor status: enforced at broadcast, still not at the `act`/login gates

`vendor_profiles.status` (`active`/`suspended`) is now genuinely enforced in one place: `BroadcastRequestAction` re-checks every submitted vendor id against `VendorProfile::where('status', Active)` itself, rather than trusting whatever list the admin's UI happened to offer -- a vendor suspended in the moment between page load and submit still can't end up invited. See `BroadcastRequestActionTest`'s "excludes a suspended vendor... even if its id was submitted" case.

Still open: **the `act`/login gates** (`app/Providers/AppServiceProvider.php`'s `act` gate, and login itself) currently only check email verification, not vendor status. Whether a suspended vendor should be blocked from logging in at all, or only from acting, is an open decision for whoever builds that enforcement — don't assume either way without deciding it explicitly first.

## The `act` gate is real enforcement, already proven — Phase 2 must actually call it

`Gate::define('act', fn (User $user) => $user->hasVerifiedEmail())` (`app/Providers/AppServiceProvider.php`) isn't just banner copy — it's a real, DB-backed check: `hasVerifiedEmail()` reads the live `email_verified_at` column, so it flips from `false` to `true` only after a genuine signed-link round trip, not on trust. Proven in `EmailVerificationTest`'s "blocks the act gate before verification and allows it after the real signed link is clicked" case: `$user->can('act')` is asserted `false`, the real `verification.verify` URL is hit over HTTP, then `$user->fresh()->can('act'))` is asserted `true` against a freshly-reloaded model.

Nothing calls this gate yet — grep confirms `AppServiceProvider.php` is the only file referencing `'act'`. That's expected; there's nothing to gate until Phase 2 exists. But it means the gate is inert until every Phase 2 request-creation entry point (buyer creating a `part_request`) and every Phase 2/3 vendor-response entry point explicitly calls `$this->authorize('act')` (or `Gate::authorize('act')` outside a Livewire component) *in addition to* whatever Policy governs the specific resource — the same defense-in-depth shape already established for `/admin` (route middleware + component-level Policy, see above). Don't assume the verification banner alone is doing any enforcement; it's purely a UI affordance sitting on top of a gate someone still has to wire in.

## Theme: light only, no dark mode

The design tokens in `resources/css/app.css` (`@theme` block: `--color-brand-*`, `--color-surface*`, `--color-ink*`, `--color-line`) define a locked light, professional palette. Never add `dark:` variants — this app does not support a dark theme.

## i18n: no hardcoded UI strings

All UI-facing text goes through `__('key')` against `lang/en/*.php`. `lang/en/app.php` holds app-wide strings; add a new file per domain area as portals are built (e.g. `lang/en/buyer.php`) rather than piling everything into one file. This keeps a future Japanese translation a matter of adding `lang/ja/*.php`, not a rewrite.

## Livewire full-page components

Routes render Livewire components directly (`Route::get('/login', Login::class)`), not through a controller method that returns a view. Livewire's default layout is already `resources/views/components/layouts/app.blade.php` (Livewire 3's own default path matches ours exactly), so no `#[Layout]` attribute is needed. Set a page title by chaining `->title(__('...'))` on the `View` returned from `render()`, not the `#[Title(...)]` attribute — attribute arguments must be compile-time constants, so they can't carry a translated string.

## Livewire components validate with Livewire's own `rules()`, not a FormRequest

`App\Http\Requests\*` FormRequest classes are for traditional controller endpoints, where the container resolves the class against the real current HTTP request. A Livewire component's `wire:submit` action doesn't have that: the AJAX payload is Livewire's own snapshot/update format, not a normal request body, so a FormRequest's `rules()` would validate against empty input. Livewire components instead define a `protected function rules(): array` method and call `$this->validate()` -- see `App\Livewire\Auth\PasswordChange`. This keeps validation in one findable place (the component class) without a request-merging workaround.

**Exception:** `App\Livewire\Auth\Login` renders a plain `<form method="POST" action="{{ route('login') }}">`, not a `wire:submit` handler, specifically so it keeps using the already-tested `AuthenticatedSessionController@store` + `LoginRequest` pair (rate limiting included). Reimplementing that inside the component would risk the two paths drifting apart on a security-critical flow. Not every Livewire "page" needs to be reactive -- a plain form post is the boring, correct choice when a tested non-Livewire path already exists.

## `EnsureMustChangePassword` and Livewire's shared update endpoint

Livewire multiplexes every component's AJAX traffic through one package-registered route, named `default.livewire.update`, running the `web` middleware group like any other route. `EnsureMustChangePassword` is appended globally to `web` (see `bootstrap/app.php`), so it must explicitly exempt `default.livewire.update` by name alongside `password.change` and `logout` -- otherwise the very request that's supposed to run `PasswordChange::update()` gets redirected away before the component method ever executes, and the form silently no-ops (200-looking network activity, no error, nothing persisted). This only surfaced under a real browser click; `Livewire::test()` mounts the component in-process and never exercises the real route + middleware stack, so it can't catch this class of bug -- see `OnboardingGateTest`'s `default.livewire.update` regression test, and prefer a real HTTP round trip (not just `Livewire::test()`) when a change touches middleware that runs on every request.

**`WithFileUploads` needs two more route names exempted the same way: `livewire.upload-file` and `livewire.preview-file`.** A `WithFileUploads` component (first used by the vendor quote-photo form) uploads via a request to `livewire/upload-file` that's entirely separate from, and happens *before*, the component's own `default.livewire.update` traffic -- so exempting only the latter isn't enough. If `livewire/upload-file` gets redirected instead of returning Livewire's expected JSON body, the browser's Livewire JS treats the redirect body as an upload error and replays it through the component's `_uploadErrored()` method on the next `default.livewire.update` call, which then throws trying to `json_decode()` a redirect response (`WithFileUploads.php`'s own `json_decode($errorsInJson, true)['errors']`) -- a real 500 on a route that itself looks correctly exempted, not merely a blocked upload. Caught and fixed the same way as the password-change regression: a real HTTP round trip hitting the actual `livewire.upload-file` route with a genuinely signed URL (`URL::temporarySignedRoute(...)`, matching how Livewire's own `GenerateSignedUploadUrl::forLocal()` builds one) and a real uploaded file, not a stand-in route -- see `OnboardingGateTest`'s file-upload regression test. One test-only wrinkle: hitting that route directly (rather than through a mounted component) skips the app-side code path that registers Livewire's `tmp-for-tests` fake disk, so the test must call `Storage::fake('tmp-for-tests')` itself first.

## `php artisan serve` on Windows strips TMP/TEMP from its spawned server process -- breaks all file uploads

The `livewire.upload-file`/`livewire.preview-file` middleware fix above (CONVENTIONS.md, same section) turned out not to be the whole story: after fixing it, the vendor quote-photo upload still crashed with the identical symptom (`WithFileUploads.php:93`, "Trying to access array offset on null" on `POST /livewire/update`). Root-caused by reproducing it with a raw multipart `curl` request straight to the real `livewire.upload-file` route -- no app code, no browser, no Livewire JS involved at all -- and getting the same failure, which meant the cause had to be below the application layer entirely.

It is: `Illuminate\Foundation\Console\ServeCommand::startProcess()` strips almost every environment variable from the PHP built-in server process it spawns when live-reload is active (the default -- no `--no-reload`), passing through only a small allow-list (`ServeCommand::$passthroughVariables`: `APP_ENV`, `PATH`, `SYSTEMROOT`, a few Herd/Xdebug/Sail-specific ones). `TMP`/`TEMP`/`TMPDIR` are not on it. Without them, PHP's own temp-directory resolution -- used both for rfc1867 multipart upload buffering and for plain `tmpfile()` calls (Livewire's `TemporaryUploadedFile` constructor calls `tmpfile()` directly) -- falls back to something that isn't writable in this environment on Windows. Confirmed by testing `php artisan serve --no-reload` (which skips this filtering entirely): the upload works. `--no-reload` disables auto-reload on `.env` changes though, so the real fix is `App\Providers\AppServiceProvider::fixServeCommandTemporaryDirectoryOnWindows()`, which appends `TMP`/`TEMP`/`TMPDIR` to `ServeCommand::$passthroughVariables` in `boot()`, gated to `PHP_OS_FAMILY === 'Windows'` -- harmless to run unconditionally otherwise (it only has any effect while `artisan serve` itself is running), and keeps live-reload working. See `tests/Unit/AppServiceProviderTest.php` for the (necessarily shallow, since there's no way to assert on a spawned subprocess's actual environment from Pest) regression test that at least locks in the array mutation itself.

The lesson for next time this class of bug shows up: if a Livewire file upload crashes on `WithFileUploads.php` trying to parse something as JSON, reproduce it with a raw `curl` multipart POST straight to the real `livewire.upload-file` route *before* assuming the cause is in application code (middleware, a Policy, an Action) -- it isolates whether the failure is happening below the framework entirely, the way this one was.

## Local dev without Redis

`.env` (gitignored, per-developer) is not required to match the locked stack (CLAUDE.md §2: Redis for queues/cache/broadcast, Reverb for real-time). On a machine with no Redis installed, running any Artisan command that touches the cache -- including `migrate:fresh` and `migrate:fresh --seed`, since spatie/laravel-permission clears its permission cache during that migration -- fails with `StreamInitException: ... [tcp://127.0.0.1:6379]` unless `CACHE_STORE`/`QUEUE_CONNECTION`/`BROADCAST_CONNECTION` are overridden locally. The fallback that needs no extra install: `CACHE_STORE=database` (the `cache` table already ships in the base migrations), `QUEUE_CONNECTION=sync` (jobs run inline, no worker needed), `BROADCAST_CONNECTION=log` (broadcast events just get logged, no Reverb server needed).

This is a **local-only, per-developer override** -- `.env.example`, CI, and production all keep the real Redis/Reverb config from CLAUDE.md §2. Before shipping anything that depends on real queue/cache/broadcast behavior (a queued job, a cache-based feature, a Reverb event), test it against the real stack, not this fallback -- `sync`/`database`/`log` can silently hide bugs that only show up with an actual worker, a real cache eviction policy, or real socket delivery.

**Same pattern for mail, optionally**: local `.env` can point `MAIL_MAILER=smtp` at [MailDev](https://github.com/maildev/maildev) (`MAIL_HOST=127.0.0.1`, `MAIL_PORT=1025`, no username/password/scheme) instead of the real driver, so a notification email can be opened and clicked in a real inbox UI instead of grepped out of `storage/logs/laravel.log`. Start it with `npx maildev` (no install step, nothing added to `package.json` -- same reasoning as not adding a `docker-compose.yml` for Redis: it's a developer-machine convenience, not a project dependency) and open `http://127.0.0.1:1080` for the inbox. Again **local-only**: `.env.example`, CI, and production stay on `MAIL_MAILER=ses` (CLAUDE.md §2 -- Phase 3 Slice 2 is where notifications actually start emailing). Tests are unaffected either way -- `phpunit.xml` hardcodes `MAIL_MAILER=array` for every test run, overriding whatever `.env` says, so `Notification::fake()`/`Mail::fake()` keep working exactly as before regardless of what's running locally.

**Mail needs the queue actually running, unlike the no-Redis fallback above**: every Phase 3 Slice 2 notification implements `ShouldQueue` with a `viaConnections()` override that pins the `database` (in-app) channel to the `sync` connection always, while leaving `mail` on whatever `queue.default` is (see `App\Notifications\QuotePresentedNotification`'s docblock) -- so the in-app bell never waits on a worker, but mail only actually sends once something processes that queue connection's jobs. The "Local dev without Redis" fallback above sets `QUEUE_CONNECTION=sync` *app-wide*, which would make mail send inline too (harmless, but means `queue:work` isn't exercised). To actually see a queued email land in MailDev: set `QUEUE_CONNECTION=database` locally (the `jobs` table already ships in the base migrations -- no Redis needed) and run `php artisan queue:work` alongside `php artisan serve`. Tests prove the split itself works end-to-end without a running worker or a real mail transport -- `NotificationChannelRoutingTest` points `queue.default` at `database` and asserts the `notifications` row exists immediately while the `mail` send only ever reaches the `jobs` table.

**Same pattern for photo uploads**: `SubmitVendorResponseAction` stores response photos to `config('filesystems.default')`, not a hardcoded `'s3'` -- so local `.env` can set `FILESYSTEM_DISK=public` (run `php artisan storage:link` once) to upload straight to `storage/app/public` instead of needing real AWS credentials or a local MinIO instance. `response_photos.disk` is saved per-row from whichever disk was actually used at upload time, so this can change later (or differ between old and new rows) without corrupting how an existing photo's disk is read back -- same reasoning as never recomputing a snapshotted price from live settings. Again **local-only**: `.env.example`, CI, and production keep the real `s3` disk from CLAUDE.md §2 -- swap this back to real S3 (or a MinIO container) before actually validating the upload path end-to-end. Tests pin `config(['filesystems.default' => 's3'])` explicitly before `Storage::fake('s3')` (see `SubmitVendorResponseActionTest`/`RequestResponseTest`) so they prove the real disk works regardless of whatever's set in the developer's own local `.env`.

## Multiple file uploads that must still work on S3: array-typed property, no `multiple` HTML attribute

`App\Livewire\Vendor\RequestResponse::$photos` is array-typed (`public array $photos`). Its file input has the `multiple` HTML attribute but is **not** bound via `wire:model`, and the drag-and-drop zone (a `<label>` wrapping that same hidden input) never binds `wire:model` either. Livewire's S3 upload driver flatly rejects a request where the client reports *more than one file selected in a single upload call* (`throw_if($isMultiple, S3DoesntSupportMultipleFileUploads::class)` in `WithFileUploads::_startUpload()`), which is exactly what `wire:model="photos"` on a `multiple` input would trigger (`$wire.$uploadMultiple()`, which always sets `multiple: true`). Instead, both entry points -- the input's `change` event and the drop zone's `drop` event -- call one shared Alpine handler (`uploadFiles(fileList)`, in the Blade view) that loops over whatever `FileList` it's given (`event.target.files` or `event.dataTransfer.files`) and calls `$wire.$upload('photos', file, ...)` once per file, awaited sequentially -- `$wire.$upload()`'s underlying `UploadManager.upload()` always sets `multiple: false` regardless of how many times it's called, so every individual upload takes Livewire's S3-safe single-file path no matter how many files arrived at once (native dialog or drag-and-drop). Sequential, not concurrent, to avoid overlapping requests against the local dev server's single-threaded built-in PHP server (see the `php artisan serve` section above). Server-side, nothing about this differs from a single-file input's own native upload: `WithFileUploads::_finishUpload()`'s "if the property is an array, but the upload ISN'T set to multiple, then APPEND" branch is what accumulates each call onto `$photos` -- the same mechanism regardless of which JS-side trigger fired. `removePhoto(int $index)` lets the vendor drop one before submitting; `updatedPhotos()` enforces the configured max (`config('vendor.max_response_photos')`, default 10 -- not a hardcoded constant, so it's easy to change later) server-side as well as hiding the drop zone/input client-side once reached, since a client could still call `$wire.$upload()` directly past the cap.

This was found the hard way, twice. First: the initial version of this feature used `wire:model="photos"` *with* `multiple`, which worked fine locally (disk wasn't S3), then broke the moment a test pinned `config(['filesystems.default' => 's3'])` for realism -- proving it would have broken in actual production too. **Test file uploads against a real S3 config, not whatever the local disk happens to be** (see the previous section) -- this class of bug is invisible otherwise. Second, after fixing that by requiring the vendor to reopen the picker once per photo (bad UX), the Alpine-driven native-multi-select replacement above surfaced its own bug: the "X of Y added" helper text was written as Blade-interpolated content inside two `<template x-if="...">` blocks (toggling between an "uploading" and an "idle" message). Since `x-if` clones/destroys its template's content rather than just hiding it, the server-rendered value baked inside got stuck showing whatever was true the one time Alpine last cloned it -- verified in a real browser: 3 photos uploaded and rendered correctly (they're plain, always-present elements), but the count text still read "0 of 6". **A Blade-interpolated value that must track a Livewire property does not belong inside `<template x-if>`/`x-show` on a `<template>` -- keep it in a plain, continuously-present element and toggle only its CSS visibility (`x-show` on the element itself, with `x-cloak` to avoid an initial-load flash) so Livewire's normal morph keeps it in sync.** See `resources/css/app.css`'s `[x-cloak]` rule, added for this.

The equivalent trap in tests: `Livewire::test(...)->set('photos', [UploadedFile::fake()->image(...)])` (an array, even with one element) makes Livewire's testing harness treat it as a multiple-file selection (`Testable::set()`: `is_array($value) && isset($value[0]) && $value[0] instanceof UploadedFile` → `$isMultiple = true`) and throws the same S3 exception a real multi-select would. To accurately simulate the real accumulate-one-at-a-time flow (which is exactly what the Alpine handler's per-file `$wire.$upload()` loop does), call `->set('photos', UploadedFile::fake()->image(...))` (a single file, not wrapped in an array) once per photo -- see `RequestResponseTest`'s multi-photo test. The array-wrapped version is kept too, as a dedicated regression test asserting it still throws `S3DoesntSupportMultipleFileUploads` -- the guard against ever reintroducing a batched upload path.

## `/admin` portal: route middleware + component-level policy, both

`App\Http\Middleware\EnsureUserIsAdmin` (aliased `admin`) guards the whole `Route::prefix('admin')` group in `routes/web.php`. Every admin Livewire component *also* calls `$this->authorize(...)` against the relevant Policy in its own `mount()` (see `App\Livewire\Admin\VendorMaster`) -- not because the route middleware is insufficient today, but because CLAUDE.md 4 treats authorization as a first-class, defense-in-depth feature: a component should refuse to mount for the wrong role even if a route were ever misconfigured. `/buyer` and `/vendor` portals should follow the same two-layer shape when they're built.

A Livewire component reusing an existing FormRequest's rules array (`protected function rules(): array { return (new CreateVendorRequest)->rules(); }`, see `VendorMaster::createVendor()`) is fine and preferred over copy-pasting the same constraints -- `rules()` is a pure array-returning method with no request-binding involved, unlike `authorize()`, so there's no request-merging hack needed to call it standalone.

## `<x-admin.temporary-password-reveal>`: a genuinely shared component, not a vendor component reused by name

When this was built for `VendorMaster` alone, its heading/warning copy was hardcoded to `admin.vendor_master.reveal.*` -- including literal text like "Vendor created". The first time it was actually reused, for `BuyerMaster`, that would have shown "Vendor created" while revealing a *buyer's* password. Fixed before it shipped: the component now takes `heading` and `warning` as plain string props the caller resolves from its own lang namespace (`admin.vendor_master.reveal.*` vs `admin.buyer_master.reveal.*`), while the truly identical copy (the "Temporary password for :company" line, Copy/Copied, the acknowledge checkbox label, the Done button) moved to a shared `admin.reveal.*` namespace the component reads directly. Both `VendorMasterTest` and `BuyerMasterTest` assert the correct heading appears *and* the other domain's heading doesn't, specifically to catch this class of copy-leak regression.

The lesson: a Blade/Livewire piece isn't proven reusable by being reachable from two call sites -- it's proven reusable once a second, genuinely different caller actually uses it and you check what it renders, not just that it renders.

## `<x-admin.profile-edit-form>`: the detail-edit view, shared the same way

`App\Livewire\Admin\VendorDetail` and `BuyerDetail` are two small, honest Livewire classes -- own properties, own `rules()`, own `save()` -- exactly like `CreateBuyerAction`/`RegisterBuyerAction` are two classes rather than one branching on a flag. What's genuinely shared between them is the *presentation*: `resources/views/components/admin/profile-edit-form.blade.php` takes a data-only contract (`title`, `backRoute`, `backLabel`, `accountFields` -- an array of `['label' => ..., 'value' => ...]` read-only pairs, `fields` -- an array of `['name' => ..., 'label' => ..., 'type' => ...]` editable inputs, `justSaved`) and renders the whole card layout, form, and saved-indicator generically. Neither Livewire class hardcodes the other's fields, and neither the component nor its lang copy hardcodes "vendor" or "buyer" anywhere -- the account block's own labels (`admin.profile_edit.name_label`/`email_label`) are domain-agnostic on purpose, learned directly from the reveal-component mistake above. `VendorDetailTest`/`BuyerDetailTest` each assert their own field labels appear *and* the other domain's don't, the same regression shape as the reveal-component tests.

Both components gate `mount()`/`save()` on `update`, not `view` -- `VendorProfilePolicy::view`/`BuyerProfilePolicy::view` also allow a vendor/buyer to view their *own* profile (for a future self-service page), which is not who this admin-only edit screen is for. `update` is admin-only on both policies, so it's the correct, stricter check here even though the surrounding `/admin` route middleware already blocks non-admins regardless -- same defense-in-depth reasoning as everywhere else in `/admin`.

## `BuyerMaster` mirrors `VendorMaster` minus suspend/resume

`buyer_profiles` has no `status` column (CLAUDE.md §7) -- there's no vendor_profiles.status equivalent to suspend or resume, so `BuyerMaster` has no `suspend()`/`resume()` methods and no status column in its table. Everything else (search, create + reveal, reset-password + reveal, the `viewAny`/`create`/`update` Policy calls in `mount()`/`openCreateForm()`/`createBuyer()`/`resetPassword()`) mirrors `VendorMaster` exactly, including reusing the role-agnostic `ResetTemporaryPasswordAction` directly (no `CreateBuyerAction`-style wrapper needed for a reset, since it doesn't touch the profile row at all).

## Email verification badge/resend on the master lists: don't reuse the `verification.send` route

Both `VendorMaster` and `BuyerMaster` show a Verified/Unverified badge (`admin.verification.*`, shared -- the `act` gate is role-agnostic, so this isn't vendor- or buyer-specific copy) and a resend button for unverified rows. The resend button calls a `resendVerification(VendorProfile|BuyerProfile $profile)` method defined directly on each component, **not** the existing `EmailVerificationNotificationController@store` (`verification.send` route) -- that controller hardcodes `$request->user()->sendEmailVerificationNotification()`, i.e. it always resends for whoever is currently logged in. Pointed at from an admin session it would resend the *admin's own* verification email, not the target vendor/buyer's -- there's no way to pass a target user through it safely without changing what the route means for its actual caller (the self-service banner in the shared layout). The admin-side method calls the same underlying `sendEmailVerificationNotification()` on the *correct* user instead, gated by the same `update` Policy check as every other action on these screens.

The resend button's "Sent." confirmation is pure Alpine state (`x-data="{ sent: false }"`), driven by calling the Livewire method directly from the click handler and reacting to its promise -- `@click="$wire.resendVerification(id).then(() => sent = true)"` -- rather than a server-tracked property like `Settings`'s `justSaved`. Same reasoning as the reveal component's copy-button: transient, purely-cosmetic feedback after a completed action doesn't need to be server-authoritative, and `$wire.method()` returning a promise is the Livewire 3-native way to hook one up from an `x-data` scope.

## `<x-admin.row-actions-menu>`: per-row dropdown, teleported to escape `overflow-x-auto` clipping

Both master lists' Actions column is a single dropdown trigger (`resources/views/components/admin/row-actions-menu.blade.php`) instead of a row of inline links -- keeps every row visually identical no matter how many actions it has, which stopped the row of links wrapping onto multiple lines and misaligning between rows once the verification badge/resend button pushed vendor rows past 4 actions. Callers pass the menu items as the slot; the component owns only the toggle/positioning chrome, the same "shared shell, caller-supplied content" shape as `<x-admin.temporary-password-reveal>` and `<x-admin.profile-edit-form>`.

**The panel is `x-teleport`'d to `<body>` and positioned with a manual `getBoundingClientRect()` calculation, not plain CSS `absolute right-0`.** Both list tables wrap their `<table>` in an `overflow-x-auto` div. Per the CSS Overflow spec, an explicit `overflow-x` forces the browser to compute `overflow-y` as `auto` too when it would otherwise be `visible` -- so a plainly `absolute`-positioned dropdown gets silently clipped at the table container's bottom edge. This isn't a rare edge case: since the panel is removed from normal flow, it never contributes to the container's height, so *any* row whose open panel would extend past where the table itself ends gets clipped -- in practice, close to guaranteed for the last row or two in any list. Teleporting to `<body>` (Alpine core, no extra library) escapes the clipping ancestor entirely; the tradeoff is that CSS's parent-relative `absolute` positioning no longer works once teleported, hence computing `top`/`left` by hand from the trigger's bounding rect and applying them via `:style` on a `position: fixed` panel. No viewport-edge collision handling (flipping upward near the bottom of the screen, etc.) -- not needed at this app's typical list lengths, and worth adding only if it actually becomes a problem, not preemptively.

## A coarse policy ability that happens to permit two roles is the wrong check for a screen only one of them owns

`PartRequestPolicy::view()` intentionally permits both an admin (any request) and a buyer (their own) -- correct for a screen both legitimately reach, but wrong the moment a screen belongs to only one of them. Building the buyer's own "my quote" page (`App\Livewire\Buyer\RequestDetail`) by reusing `view()` (since it already encodes "buyer sees their own") looked reasonable, but it also let an admin's session mount a buyer-only component in a `Livewire::test()` -- the same class of gap `viewBoard` vs `view` already exists to close on the admin side (CLAUDE.md 4), just discovered again from the other direction. `viewAny()` had the identical problem for the buyer's list page (it permits `isAdmin() || isBuyer()`, "for a still-hypothetical shared use" per its own docblock, but nothing in the codebase actually shares it that way -- the admin board uses `viewBoard()` instead).

Fixed by adding two more single-role, no-bypass abilities alongside the existing ones: `viewOwnRequests()` (buyer-only, list) and `viewOwn()` (buyer-and-owner-only, one request) -- mirroring `viewVendorInbox()`/`respond()`'s shape on the vendor side exactly. The lesson generalizes: **when a new screen belongs to exactly one role, check whether the "obvious" existing ability that matches its data access also happens to permit a different role for a different screen's sake -- if so, it's the wrong ability, not a shortcut.** A route-level access test alone won't catch this (the `buyer` middleware blocks the wrong role anyway); it only surfaces in a `Livewire::test()`-level authorization test, which is exactly why every isolation-sensitive page gets one of those too, not just the HTTP-level test.

## The buyer's presented-quote view: don't just avoid a public model property, avoid passing the vendor's model into the Blade view at all

`App\Livewire\Buyer\RequestDetail` follows the by-now-standard shape (only `public int $partRequestId`, an explicit `->select()` column allowlist on every `render()`) -- but this page goes one step further, because what it must hide isn't on the `part_requests` row at all: it's on the *vendor's own response* (`cost_price`, and the response's `vendor` relation). Fetching the selected `VendorResponse` and handing the whole model to the Blade view would rely on the view never writing `$quote->vendor` or `$quote->cost_price` -- a discipline that erodes the first time someone adds a field to the comparison screen and copies a snippet over without re-deriving what's safe here. Instead, `presentedQuote()` builds a plain array literal with exactly two keys (`quality_rank`, `photos`) and nothing else -- there is no `->vendor` or `->cost_price` to reach for by mistake, because the value doesn't have one. Prefer this "narrow, hand-built read shape" pattern over "pass the real model and trust the view" whenever what needs hiding lives on a *related* model, not just extra columns on the one already being queried.

## Testing a component's `mount()`-level authorization: expect a 403 response, not a thrown exception

`Livewire::test(SomeComponent::class)` for a component whose `mount()` calls `$this->authorize(...)` does **not** let a failed check's `AuthorizationException` propagate to the test. Livewire's initial-render test harness (`RequestBroker::temporarilyDisableExceptionHandlingAndMiddleware`) explicitly keeps `AuthorizationException` (and `HttpException`) routed through the real exception handler while every other exception type is left to throw raw -- so a blocked mount comes back as an ordinary 403 response. Assert it the same way you would a controller response: `Livewire::actingAs($user)->test(Component::class)->assertForbidden()` (Livewire's `Testable` proxies unknown assertion calls straight to the underlying `Illuminate\Testing\TestResponse`). See `VendorMasterTest`'s two "does not let a buyer/vendor mount" cases.

## Two buyer-creation paths, two separate Actions -- not one shared with a flag

`CreateBuyerAction` (admin-created, mirrors `CreateVendorAction`) and `RegisterBuyerAction` (self-registration) both create a `User` + `BuyerProfile`, but differ in almost everything else: who's authorized to call it (an admin vs. nobody -- it's a public route), where the password comes from (system-generated temp password vs. user-chosen), `must_change_password` (`true` vs. `false`), and whether a verification email needs sending (no -- deferred to first login via the resend banner -- vs. yes, immediately). Two small, honest classes beat one action with a `bool $isSelfRegistration` branching through all of that. `CreateAdminManagedUserAction` stays the shared piece *only* for the part that's genuinely identical across buyer/vendor admin-created accounts.

## Buyer `member_code` is derived, not stored-then-checked

`BuyerProfile::generateMemberCode(User $user)` returns `'BYR-' . str_pad($user->id, 6, '0', STR_PAD_LEFT)` -- deterministic from the user's own already-unique, auto-increment id. No separate uniqueness check or retry loop needed, unlike a randomly-generated code would require. Never a form field (self-registration or admin-created) -- always system-generated after the `User` row exists, since it needs that id.

## Email verification is a banner, not a blocking page

CLAUDE.md 14's universal invariant is that verification gates *acting*, not browsing -- so there's no Laravel-stock `verified` middleware redirect to a dedicated `verification.notice` page anywhere in this app (that route doesn't even exist). Instead, the shared layout (`resources/views/components/layouts/app.blade.php`) shows an inline amber banner for any authenticated-but-unverified user, with a "resend" button that posts to `verification.send` and redirects back to wherever the banner was shown (`session('status')`, the existing flash-banner pattern). Only two routes exist: `verification.verify` (the signed link from the email, `Illuminate\Foundation\Auth\EmailVerificationRequest` handles signature validation) and `verification.send` (resend). Both live under `App\Http\Controllers\Auth`, not Livewire -- a signed GET link clicked from an email client, and a plain resend POST, have no need for AJAX interactivity.

A best-effort side effect (like sending that verification email) belongs *after* the DB transaction commits, wrapped in try/catch + `report()`, never inside the transaction -- a mail failure must not roll back an otherwise-successful write (CLAUDE.md 10). See `RegisterBuyerAction::execute()`.

**Open item for Phase 3**: the verification email is currently Laravel's unmodified default `Illuminate\Auth\Notifications\VerifyEmail` template/styling -- functionally correct (confirmed working end-to-end against the real log-driver output) but not branded. When SES lands in Phase 3, give it the app's own look (light theme, `app.name`) rather than shipping the framework default to real inboxes -- either a custom `MailMessage` build in a `App\Notifications\VerifyEmail` override, or a markdown mail theme.

## Shipping is rule-based (weight brackets), calculated at presentation -- superseded the earlier fixed vehicle/container settings

**Superseded design, kept here for history**: the app originally exposed `shipping_fee_vehicle`/`shipping_fee_container` as flat, admin-editable `settings` values, selected by the buyer at checkout. That's gone -- removed from `settings`, from the Settings screen, and from checkout entirely. Don't reintroduce a `shipping_fee_vehicle`/`shipping_fee_container` settings key or a checkout-time method picker; if either turns up in new code, it's a regression to the old model, not a feature.

**Current model (CLAUDE.md §14 Phase 4, v1)**: `App\Models\ShippingWeightBracket` (table `shipping_weight_brackets`: `upper_kg`/`fee`/`order`) is the admin-configurable lookup, and `App\Services\ShippingCalculator` picks the smallest bracket whose `upper_kg` covers a given weight (a `null` `upper_kg` is the top/catch-all bracket, for heavy items like engines). `App\Actions\PresentQuoteAction` calls it at **quote-presentation time**, not checkout -- using the vendor response's own `weight_kg` -- and snapshots the result onto `presented_quotes.shipping_fee`, alongside `shipping_fee_overridden`/`shipping_fee_override_reason` if the admin overrode the calculated figure (a reason is required whenever overridden, enforced by the Action, logged via `PresentedQuote`'s existing `LogsActivity`). `App\Actions\SelectQuoteAction` copies that fee onto `part_requests.shipping_fee` the same way it already copies `buyer_price`, so by the time the buyer reaches checkout the fee is fixed and read-only -- `CheckoutAction` no longer accepts or computes a shipping method at all.

**DHL is still deferred, for the same underlying reason as before**: it requires the *client's own* DHL Express (MyDHL) business account for a real rate/"Rating" API, and whether they have one is still unconfirmed. It isn't a `settings` key or a checkout option today; when it's built, it'll be a second method alongside the weight-bracket one, not a replacement for it.

**A DB-backed `$table->enum()` column needs its own migration when the PHP enum's cases change -- the model's `$casts` array alone isn't enough.** `part_requests.shipping_method` was created as a native MySQL `ENUM('dhl', 'vehicle', 'container')` (`create_part_requests_table`). Renaming `App\Enums\ShippingMethod`'s cases to `Standard`/`Dhl` compiled and passed the whole Pest suite immediately -- because the *test* connection is sqlite, where Laravel's `enum()` has no real constraint to violate. Only a real browser run against MySQL surfaced it, as `SQLSTATE[01000]: ... Data truncated for column 'shipping_method'` the moment `SelectQuoteAction` tried to write `'standard'` -- the column's own allowed values still only recognized the old three strings. Fixed with a follow-up migration (`update_shipping_method_enum_on_part_requests_table`) that widens the enum first (union of old and new values), reassigns any existing `vehicle`/`container` rows to `standard`, then narrows to the final set -- narrowing before reassigning rejects the very UPDATE meant to fix the data, with the identical truncation error. Guarded to `DB::getDriverName() === 'mysql'` (a no-op, not skipped coverage, on sqlite). **The lesson: changing a PHP backed enum's cases where the underlying column is a native DB enum (not a plain string/varchar) always needs a paired ALTER migration, and Pest alone won't catch a missing one -- verify against the real database driver, not just the test suite, whenever a native-enum column's cases change.**

**Open client question, not yet answered**: does the client have their own DHL Express business account? Nothing DHL-API-shaped should be scoped or built until that's confirmed.

## Every form: required asterisks, example placeholders, brief help text

Every form field in the app follows the same three-part standard, applied consistently rather than left to per-form judgment:

- **Required fields get a red asterisk** right after the label text, via the shared `<x-required-mark />` component (`resources/views/components/required-mark.blade.php` -- a bare `<span class="text-red-600">*</span>`). Which fields get the mark comes straight from that field's actual validation rules (the FormRequest's or Livewire component's `rules()`) -- not from copying a reference mockup's asterisks, which may not match our schema's own nullability (e.g. the client's prototype marks VIN as required; our `part_requests.vin` column is nullable, so our form doesn't mark it).
- **Placeholders show an example value in the expected format**, wherever the format isn't self-evident from the label alone (a VIN, an OEM part number, a URL). Skip them where they'd add nothing (a plain name field) or where they'd be actively confusing (never on a password field).
- **A short line of help text under the field**, only where the field's purpose or optionality genuinely isn't obvious on its own (e.g. "Optional, but helps vendors confirm an exact fit." under an optional VIN field). Don't add one to every field just for symmetry -- CLAUDE.md's "don't add features beyond what's needed" applies to hint text too.

All three go through `lang/en/*.php` like every other UI string -- see `App\Livewire\Buyer\RequestForm` and `lang/en/buyer.php`'s `request_form` section for the reference implementation.

## Vendor response (打診 reply): never bind the full model as public Livewire state on an isolation-sensitive page

`App\Livewire\Vendor\RequestResponse` keeps only `public int $partRequestId`, never `public PartRequest $partRequest`. A public Eloquent-model property gets its full attribute set serialized into Livewire's client-side snapshot (visible in page source/dev tools) -- on a page a vendor's own browser loads, that would put `buyer_id` (and everything else on the row, including columns the Blade view never renders) directly into their hands, regardless of how careful the view itself is. `mount()` still receives the full `PartRequest` via Laravel's normal route-model binding (needed to call `$this->authorize('respond', $partRequest)`), but only extracts `->id` before discarding it; `render()` re-fetches with an explicit `->select([...])` every request instead of trusting stored state. Same reasoning drove `App\Livewire\Vendor\Inbox`'s list query: an explicit column allowlist, not a bare `PartRequest::query()->get()`, so `buyer_id` is never loaded into memory at all on a vendor-facing screen.

The same shape (structural Policy check + Action re-verifies the specific business rule) as `BroadcastRequestAction`/`PartRequestPolicy::broadcast` repeats here: `PartRequestPolicy::respond()` is the one place "was this vendor actually invited to this request" is checked, and both the page's `mount()` and `SubmitVendorResponseAction::execute()` call it/re-derive it independently rather than one trusting the other.

## Stripe: confirmation is webhook-only, never the checkout request itself

**The core invariant**: nothing except `App\Actions\ConfirmStripePaymentAction`, called exclusively from `App\Http\Controllers\StripeWebhookController` after it has verified the webhook's signature, is ever allowed to set a Stripe payment's `payments.status` to `confirmed`. Not `StripePaymentGateway::charge()`, not anything reachable from a browser redirect. A signed webhook can't be forged by the buyer's own browser; a redirect landing back on our site proves nothing (a buyer could navigate there directly without ever paying).

**This creates a real, deliberate consequence**: `App\Actions\CheckoutAction` is completely unmodified by the Stripe integration (the whole point of the `PaymentGateway` abstraction, CLAUDE.md §14 Phase 4 slice 1) -- it still flips `part_requests.status` to `paid` synchronously, the moment `charge()` returns success. For Stripe, "success" only ever means "the PaymentIntent was created", not "money moved" -- so for a real charge, there's a real (short) window where a request reads `paid` while its `Payment` row still reads `pending`. This is safe specifically because the actual money-critical gate (`ConfirmOrderToVendorAction`, CLAUDE.md §6.3) independently requires a `confirmed` `Payment` row on top of `status === paid` -- it was never written to trust `paid` status alone, and doesn't need to change for this integration either. See `tests/Feature/StripeCheckoutFlowTest.php` for the full walk-through: checkout → gate still closed → webhook fires → gate opens.

**Don't "fix" this by making `charge()` mark the payment confirmed synchronously** (mirroring `StubPaymentGateway`) -- that would silently reintroduce trusting something other than the webhook, defeating the entire reason this slice exists. If the `paid`-before-`confirmed` window ever needs to disappear (e.g. buyer-facing copy that currently says "Payment confirmed" reads wrong during that window), fix it in the UI layer or by rethinking what `paid` status means -- not by weakening the webhook-only guarantee.

**Amounts**: JPY is one of Stripe's own zero-decimal currencies, and this app already stores money as integer yen (CLAUDE.md §6.1/§7) -- `$payment->amount` is passed to Stripe completely as-is in `StripePaymentGateway::charge()`. Don't multiply by 100 the way a decimal currency (USD, EUR) would need; that's a 100x overcharge bug waiting to happen if this ever grows a second currency.

**Idempotency, two different layers**: the checkout button's own `wire:loading.attr="disabled"` (already in place, `resources/views/livewire/buyer/checkout.blade.php`) is the browser-level double-click guard. Separately, `StripePaymentGateway::charge()` passes a `Stripe\Util\RequestOptions` `idempotency_key` derived from `"checkout_payment_{$payment->id}_create"` -- Stripe's own API-level backstop against a retried `create()` call for the *same* `Payment` row producing a second `PaymentIntent`. Two different failure modes, two different guards; neither alone covers both.

**Testing Stripe without ever calling the real API**: don't mock `StripeClient` or its lazily-constructed service objects (`->paymentIntents` etc. are magic `@property`-only properties on the concrete class, awkward and brittle to mock directly, and PHPStan can't see through a mock of the interface at all -- `Stripe\StripeClientInterface` doesn't declare them). Instead, swap Stripe's own HTTP transport: `\Stripe\ApiRequestor::setHttpClient($fake)` where `$fake` implements `\Stripe\HttpClient\ClientInterface` and returns a canned `[jsonBody, statusCode, headers]` tuple. The real SDK code (request building, response parsing, object hydration) all runs for real; only the network call is faked. Always reset with `ApiRequestor::setHttpClient(null)` in `afterEach()` so a faked transport can't leak into another test file (the SDK lazily recreates a real `CurlClient` the next time one is needed). See `tests/Unit/Payments/StripePaymentGatewayTest.php`.

**Testing the webhook's signature verification for real**: `\Stripe\WebhookSignature::generateSignatureHeader($payload, $secret)` is a public SDK helper explicitly meant for this ("useful for signing payloads in unit tests") -- it computes the exact same `t=...,v1=...` HMAC-SHA256 header Stripe itself would send. Build a genuinely-valid signed request this way for the happy-path tests, and reuse it with a wrong secret / tampered body / missing header entirely for the "must reject a forged POST" tests -- see `tests/Feature/StripeWebhookTest.php`. Post with Laravel's low-level `$this->call('POST', $uri, [], [], [], $server, $rawJsonString)` (not `postJson()`) so the exact bytes you signed are the exact bytes the controller's `$request->getContent()` sees.

**The webhook route needs its own CSRF exemption** (`bootstrap/app.php`'s `validateCsrfTokens(except: [...])`) -- Stripe's server has no session and sends no token. The signature check is what stands in for both authentication and CSRF here; a route with neither a valid signature nor a recognizable session has no other guard.

**Superseded design, kept here for history**: Elements was originally initialized in Stripe's "deferred" mode (`stripe.elements({mode: 'payment', amount, currency, paymentMethodTypes: ['card']})`, no PaymentIntent yet), with the real PaymentIntent created later at submit time and its `clientSecret` passed *separately* into `stripe.confirmPayment({elements, clientSecret, confirmParams})`. That fixed an earlier bug (Elements and the PaymentIntent disagreeing on `payment_method_types` -- one "automatic", one explicit -- made `confirmPayment()` fail outright with "Payment details were collected through Stripe Elements using automatic payment methods and cannot be confirmed through the API configured with payment_method_types"), by pinning `paymentMethodTypes: ['card']` on **both** sides. It passed every automated test and even an initial live locale/error-message check. It did **not** survive a full live payment: see the next section for what actually broke and why the whole pattern was replaced, not patched again.

## Stripe: a live payment can confirm a *different* PaymentIntent than the one the backend created -- the deferred-Elements pattern is not safe enough for this app

**What happened, concretely**: a buyer completed a real test-mode card payment. `StripePaymentGateway::charge()` had created and stored PaymentIntent `pi_3UIMpY6cEgCpnV2c0kiLd4Um` on the `Payment` row (`gateway_reference`). The webhook that actually arrived, seconds later, was for `payment_intent.succeeded` on `pi_3UIMqVKwoSBExekl2O6y4Dtq` -- a **different id, no matching `Payment` row anywhere in the database**. `StripeWebhookController` correctly logged "Stripe webhook: payment_intent.succeeded for an unknown PaymentIntent" and did nothing (exactly as designed -- an unrecognized intent must never touch a payment row). The payment stayed `pending` forever and the §6.3 gate never opened. Every one of this app's *own* Stripe payment rows created during live testing was still `pending` at the time this was investigated -- this was systemic, not a one-off.

Server-side, everything checked out: `CheckoutAction::execute()` creates the `Payment` row, calls `$gateway->charge($payment)` which creates the PaymentIntent and updates `gateway_reference` with its id, all inside one `DB::transaction()` -- and `Checkout::pay()` only ever returns the `client_secret` belonging to that same, just-committed row. There is no code path on the backend that could hand the browser a `client_secret` for any intent other than the one just stored. The divergence traced to the **frontend's own Elements initialization**: the deferred pattern (`stripe.elements({mode, amount, currency})`, no `clientSecret` at creation, one passed separately to `confirmPayment()` later) is Stripe's own documented pattern and matches its docs verbatim -- but it is the *less* constrained of Stripe's two integration styles, and live testing showed it does not reliably guarantee that what gets confirmed is the exact intent whose secret was passed in.

**The fix: initialize Elements directly with the real PaymentIntent's own client secret**, `stripe.elements({clientSecret})`, instead of the deferred `{mode, amount, currency}` form. This makes the mismatch structurally impossible: from the moment Elements exists, there is exactly one `clientSecret`/PaymentIntent anywhere in the component's JS, and `stripe.confirmPayment({elements, confirmParams})` doesn't even take a separate `clientSecret` argument any more -- it uses the one Elements already carries. As a side effect, `paymentMethodTypes: ['card']` is no longer set on the frontend at all -- a PaymentIntent-scoped Elements instance automatically inherits the *intent's own* `payment_method_types` (still `['card']`, set server-side in `StripePaymentGateway::charge()`), so there's no longer a second, separately-maintained copy of that setting to keep in sync.

**This requires the PaymentIntent to exist *before* Elements/the card form can mount**, which is a real trade-off against the original "deferred" design's whole point (avoid creating a real charge attempt -- and flipping `part_requests.status` to `paid` -- from a bare page view). The fix is an explicit, buyer-driven two-phase flow rather than eagerly creating the intent the moment the card step becomes reachable:

1. **"Proceed to payment"**: once an address is selected, the Card details section shows a `proceed_to_payment_button` prompt, not the card form. Clicking it calls `Checkout::pay()` (creating the `Payment` row + PaymentIntent, exactly as before -- this is still the buyer's own explicit commitment to paying, never a side effect of merely loading the page), then `proceedToPayment()` initializes `elements` with the returned `clientSecret` and mounts the Payment Element for the first time.
2. **"Pay now"**: once the card form is actually showing (Alpine's `cardMounted` flips true), the same submit button becomes step 2 -- `elements.submit()` then `stripe.confirmPayment({elements, confirmParams, redirect: 'if_required'})`, confirming the exact intent Elements was initialized with. A decline just re-runs this step; `Checkout::pay()`/`CheckoutAction` never runs a second time for the same page load.

The `<form>`'s single `@submit.prevent="cardMounted ? submit() : proceedToPayment()"` dispatches between the two steps, and the Payment Element's mount `<div>` stays permanently in the DOM (`x-show="cardMounted"`, never a Blade `@if`) from the moment the card step is reachable, so `$refs.paymentElement` always resolves whenever `proceedToPayment()` needs it.

**One more consequence worth knowing**: `CheckoutAction` snapshots the shipping address (`SnapshotShippingAddressAction`) inside the same transaction as creating the charge -- so once "Proceed to payment" has succeeded, the address is permanently locked in for this request. Switching the address radio after that point (still technically possible, still deferred/non-wiping per the section below) would silently do nothing. The radios disable themselves once Alpine's `cardMounted` is true (`:disabled="cardMounted"`) rather than let the buyer believe a switch at that point still works.

Not yet built: any cleanup/expiry for a buyer who clicks "Proceed to payment" and then abandons the page before ever submitting a card -- that leaves a `paid`-status request with a permanently `pending` `Payment` row and no way back into checkout (`isEligible` requires `status === Quoted`). This was a known, accepted trade-off of the *previous* one-click design too (the intent was already created by the time card details were typed); the two-phase flow doesn't make it worse, but doesn't fix it either.

**A cached config (`bootstrap/cache/config.php`) freezes `.env` values for every app boot, tests included -- and there's no per-environment cache file.** If a developer runs `php artisan config:cache` (or something else does it, e.g. as part of live-testing setup) while their local `.env` has `PAYMENT_GATEWAY=stripe` and real Stripe keys, that gets baked into the cache and used for `php artisan test`/`pest` too -- `phpunit.xml`'s `<env>` overrides are completely bypassed once a config cache file exists, since Laravel loads the cached array directly instead of re-resolving `env()` calls. Symptom: previously-green tests suddenly fail in confusing, seemingly-unrelated ways (a checkout test getting a `pending` payment instead of `confirmed` because it silently resolved the real `StripePaymentGateway`; unrelated auth tests throwing CSRF 419s because the cached config also froze `APP_ENV`/`SESSION_DRIVER` at whatever they were for local dev). Fix: `php artisan config:clear`. As a second line of defense, `PAYMENT_GATEWAY` is now explicitly pinned to `stub` in `phpunit.xml` itself, the same way `DB_CONNECTION`/`SESSION_DRIVER`/etc. already are -- never rely on a config file's own `env()` fallback alone for something this money-critical. Never commit `bootstrap/cache/*.php`, and don't leave a config cache in place while actively developing -- it's a deploy-time optimization, not a local-dev habit.

**Once the buyer has reached the Stripe card step, `Checkout::pay()` must never let Livewire do a normal re-render -- success or failure.** `pay()` is now the server side of the "Proceed to payment" click (see the two-phase flow above) -- on success it flips `part_requests.status` to `paid`, which would immediately flip `render()`'s `$isEligible` to false and morph the *entire* checkout form away into the "not eligible" message, right as the browser's JS continuation tries to mount the Payment Element into a `<div>` that would no longer exist. `Checkout::pay()` computes `$protectCardForm = $this->cardStepReady(isFree: false)` and calls `skipRender()` *before* `$this->validate()` can even throw, so every failure from that point on -- a validation exception, `CheckoutNotAllowedException`, a declined charge, anything -- reports back through the method's own return value (`{error: '...'}`) instead of `addError()`. The Alpine `proceedToPayment()` function checks `result.error` the same way it checks `result.clientSecret`. Before an address is selected, `$protectCardForm` is false, so `pay()` keeps the classic validate-then-error-bag behavior Blade's own `@error('selectedAddressId')` renders -- unchanged for the stub gateway and for a buyer who hasn't reached the card step at all. (This guard predates the two-phase redesign -- it was originally written to protect an *already-mounted* Payment Element from a wiping re-render when `pay()` ran at final-submit time; the reasoning generalized cleanly once `pay()` moved earlier in the flow, since a "paid" status flip is exactly as re-render-unsafe before the Element mounts as after.)

**The better fix is prevention, not just damage control: never let the buyer reach the card step without a shipping address in the first place.** `Checkout::mount()` already pre-selects the buyer's default address (`$this->selectedAddressId = $defaultAddressId`), so this only ever affects a buyer with zero saved addresses. `Checkout::cardStepReady(bool $isFree): bool` (`$this->isStripeGateway() && ! $isFree && $this->selectedAddressId !== null`) is the single source of truth `render()`, `pay()`, and `addAddress()` all read -- **not** the same thing as the Payment Element actually being mounted in the browser (that's the separate, later, buyer-driven `cardMounted` Alpine flag from the two-phase flow above). The Blade view gates the entire Stripe-driven form (the `x-data`/`x-init`/`@submit.prevent` attributes on `<form>`) behind `$cardStepReady` -- with no address, the form silently falls back to the plain `wire:submit="pay"` branch (nothing Stripe-related exists yet, so a normal re-render there is completely safe) and the Card details section shows an upfront `buyer.checkout.address_required_for_payment` message instead, with the submit button disabled. The moment the buyer adds an address inline (`addAddress()`), the resulting re-render is the *first* time the Stripe form's `x-data` appears in the DOM at all -- see the reload note below for why that specific transition needs its own handling.

**The same wiping-re-render bug also applies to switching between *existing* saved addresses once the card step is reached -- a mainstream case (multiple addresses is a supported feature), not an edge case, and needed its own fix.** The address radios read `$cardStepReady` to decide how they sync:

- **Before the card step is reached**, the radios keep `wire:model.live="selectedAddressId"` -- selecting one *must* trigger an immediate re-render, since that's what reveals the card step (or lifts the "please select an address" block) in the first place. Nothing Stripe-related exists yet, so there's nothing to protect.
- **Once the card step is reached**, the radios switch to a *deferred* `wire:model="selectedAddressId"` (no `.live`) -- clicking a different radio no longer fires any request at all, so there's no re-render to risk. The buyer's eventual choice still reaches the server correctly: Alpine's `proceedToPayment()` calling `this.$wire.pay()` carries along whatever's deferred, exactly the same way a native HTML form submit carries every field's current value. Once the real PaymentIntent has been created (Alpine's `cardMounted` true), the radios additionally disable themselves (`:disabled="cardMounted"`) -- `CheckoutAction` has already snapshotted the shipping address by then (`SnapshotShippingAddressAction`, same DB transaction as the charge), so a switch at that point would silently do nothing; disabling is the honest UI rather than a switch that looks like it worked.
- Deferring the model update also meant the **visual "selected" highlight could no longer be a PHP-computed class** (`{{ $selectedAddressId === $address->id ? '...' : '...' }}`) -- that only updates on a render, which is precisely what's no longer happening. It's now pure CSS instead: the `<label>` uses Tailwind's `has-checked:border-brand-500 has-checked:bg-brand-50`, which reacts to the browser's own native `:checked` state on the radio inside it -- instant, and needs no Livewire round trip at all.
- Switching to a deferred model surfaced one more thing that had been silently relying on the `.live` round trip to paper over it: **the radio inputs had no `name` attribute.** Livewire had been directly setting each radio's `.checked` property from the server on every live round trip, so exactly one was ever checked regardless of native grouping. With no round trip happening on click any more, the *browser's own* native mutual-exclusivity (which requires a shared `name` across a radio group) is the only thing left enforcing "only one checked at a time" -- so all the address radios now share `name="selectedAddressId"`.

Together this means a buyer can freely switch between saved addresses right up until they click "Proceed to payment", without losing any in-progress state -- confirmed by `tests/Feature/Livewire/Buyer/CheckoutTest.php`'s "switch to a different saved address" tests (asserting the rendered markup uses the right binding mode + shared `name` + `:disabled` in each state, and that the final `pay()` call correctly uses whichever address the buyer landed on).

**Adding a *brand-new* address (`addAddress()`) needed a different fix entirely -- a full page reload, not a DOM-level workaround.** Unlike switching between addresses that already exist (no new markup, just a value change -- handled above), adding one requires genuinely new markup (a new radio) to appear, so a deferred client-side update alone can't cover it. This matters specifically for **the buyer's very first address** (`cardStepReady` flips false → true on this response): the `<form>` gains `x-data`/`x-init`/`@submit.prevent` for the first time via a Livewire morph that only changes its *attributes* -- the element itself already existed. Alpine reliably initializes a directive when the element carrying it is first *inserted* into the DOM, not when an existing element's attributes change underneath it, so this doesn't reliably boot the Alpine component at all. Live symptom: the Pay button rendered half-initialized after adding a first address -- collapsed height, its label text missing, because its `x-text` binding never actually took.

The fix: `Checkout::addAddress()` checks the same `cardStepReady()` the view uses (computed *after* the new address is saved and auto-selected, so it reflects the state the buyer is about to land in) and, if true, calls `$this->redirect(route('buyer.requests.checkout', $this->partRequestId))` instead of letting the response render in place. A full page reload sidesteps the whole Alpine-adoption question by construction -- it boots Alpine fresh, exactly like the buyer's original page load, with the new address already selected. The stub/free paths are untouched (`cardStepReady()` is always false there, so `addAddress()` keeps its plain in-place update + success toast).

## Payment-confirmed notifications: one shared Action, fired from three different confirmation points

`App\Notifications\PaymentConfirmedNotification` (buyer) and `PaymentConfirmedAdminNotification` (all admins) are the Phase 3 notification system's 8th and 9th events, following the existing seven exactly (`ShouldQueue`, `viaConnections()` pinning `database` to `sync` while `mail` defers to the queue, all copy in `lang/en/notifications.php`). What's different is *where* they fire from: every other notification has exactly one Action that produces its event. A confirmed payment has **three** -- `CheckoutAction` (the stub gateway, which confirms synchronously inside its own `charge()`), `ConfirmStripePaymentAction` (the webhook-only confirmation point for a real Stripe charge), and `ConfirmFreeOrderAction` (a 無償 request's ¥0 confirmed payment) -- and all three need to notify the exact same way.

Rather than duplicate the same two `notify()` calls (and their own try/catch pairs) three times, `App\Actions\SendPaymentConfirmedNotificationsAction::execute(Payment $payment)` is a small, single-purpose Action whose only job is composing the existing two notifications -- **not** a generic `NotificationService` (CLAUDE.md §8 still applies), just the same "an Action can depend on another Action" shape `CheckoutAction`/`ConfirmFreeOrderAction` already use for `SnapshotShippingAddressAction`. It absorbs both notify calls' own `try/catch(Throwable)`+`report()` internally (same "two independent side effects, two separate catches" discipline as `RegisterBuyerAction`), so none of its three callers need a try/catch of their own around it -- CLAUDE.md §10's best-effort/never-rolls-back guarantee is the *action's own* contract, not something each caller has to remember to provide.

**Fired only from the genuinely-new-confirmation path, never from an already-confirmed one.** `ConfirmStripePaymentAction` has an early return for a redelivered webhook (`if ($payment->status === PaymentStatus::Confirmed) { ...log and return; }`, since Stripe's at-least-once delivery means the same `payment_intent.succeeded` event can arrive more than once) -- `SendPaymentConfirmedNotificationsAction` is called only *after* that guard, from the branch that actually just transitioned the payment to confirmed. Get this backwards (or call it unconditionally) and a buyer/admin would be notified again on every redelivery of the same event. `CheckoutAction` needs the equivalent care for a different reason: `charge()` runs *inside* its own `DB::transaction()`, so whether the payment ended up confirmed (stub) or still pending (Stripe, confirmed later by the webhook) is only known *after* the transaction commits -- the closure returns a `[$partRequest, $payment]` tuple instead of `PartRequest` alone (same for `ConfirmFreeOrderAction`, which always confirms and always notifies) specifically so the caller can check `$payment->fresh()->status` post-commit before deciding whether to fire. Confirmed by `ConfirmStripePaymentActionTest`'s "does not send a duplicate payment-confirmed notification when a webhook is redelivered" and `CheckoutActionTest`'s "never sends a payment-confirmed notification when the gateway declines the charge".

## Testing

- Unit tests for pure business logic live under `tests/Unit`, grouped by the class under test (e.g. `tests/Unit/Services/PricingServiceTest.php`).
- Use `uses(RefreshDatabase::class)` per-file (see `tests/Pest.php` for the base `TestCase` binding) whenever a test touches the DB, even in `tests/Unit`.
- Prefer a Pest `->with([...])` dataset over duplicate `it(...)` blocks when the same assertion needs to hold across many inputs (see `PricingServiceTest`'s "holds for any configured rate/minFee" case).
